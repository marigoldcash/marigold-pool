# Marigold mining pool — build plan

A step-by-step plan for building `marigold-pool`, the mining pool that runs on the big rig (pve3) and lets ASICs and CPU wallets mine together and be paid by share. It is written to be executed by a model session one step at a time: each step says what to build, which tests prove it, and the exact verify command whose pass is the only thing that lets the box be ticked. Decided 2026-10-12 (founder): the pool lives in its **own public repository**, `marigoldcash/marigold-pool`, depends on the node repository's crates by git pin, and **also serves Kaspa** from the same codebase, so an operator installs and learns one piece of pool software (M11). This file is the repository's `PLAN.md`; the hand-over copy is `docs/marigold/MINING-POOL-PLAN.md` in `marigoldcash/marigold` and is not kept in sync after this point.

Background and the survey of what could be cloned: PLAN.md step P9.4b in `marigoldcash/marigold`. Short version: Kat Pool's Rust pool (`Nacho-the-Kat/katpool`, MIT/Apache) is the reference reading, nothing is vendored from it — its accountant is bound to PostgreSQL and KRC-20, and our bridge is newer than theirs — so the pool is written fresh against this plan, with their `docs/architecture.md` and `accountant/src/allocation.rs` open for comparison when a step says so.

## Ground rules

1. **Two checkouts.** The pool repository is the working directory. Steps marked **[marigold]** are done in a checkout of `marigoldcash/marigold` at `../marigold` (branch `main`), committed and pushed there, and the pool's dependency pin is then moved to that commit. Nothing else in `marigold` is touched.
2. **Build and test on pve3, never locally.** `scripts/remote-build.sh` (created in M0) mirrors the tree to pve3 and builds there; `TEST=1 scripts/remote-build.sh` runs `cargo test --workspace` there. Every build bumps the version (`scripts/bump-version.sh`, M0), so any binary traces to its commit.
3. **Commits.** Author and committer are `Dom <leancode@users.noreply.github.com>`. The commit message starts with the step ID (`M3: shares from bridge events`). No AI attribution of any kind, in commits, comments, docs or PR bodies. One step may be several commits; a step is done only when its ✅ *Verify* passes, and the box is ticked in the same commit as the last change.
4. **Toolchain.** The pool pins the same `rust-toolchain.toml` as `marigold` (1.98.1 on 2026-10-12; copy the file, keep it identical). `cargo fmt --check` and `cargo clippy --workspace --tests -- -D warnings` are part of every verify.
5. **Words.** The smallest unit is the **petal** (100,000,000 per MAGLD); never "sompi" in any string a person can see, and amounts shown to people are MAGLD with two decimals. The money bucket is a **wallet**, never a vault. Every message on the dashboard or in an API error is readable by someone's grandmother: what happened and what to do, no jargon.
6. **No float money.** Petals are `u64` everywhere money is computed. Share weights are integers. Allocation is a pure function, tested for exact sums.
7. **Hosts are the founder's.** No firewall changes, no nginx edits, no new systemd units enabled without the step saying so. Never kill a process by name on pve3; by exact PID only. Secrets (the pool wallet secret) are placed by the founder; the plan never prints one.
8. **Chain-neutral core.** Only the `Chain` backend (see Architecture) may name a chain: nothing in `pool-domain`, `pool-db`, `pool-accountant`, `pool-payout` or `pool-api` imports a `kaspa-*` crate directly or hard-codes a prefix, ticker, unit name, port or maturity; those come from the `Chain` implementation selected at build time. A step that breaks this rule is not done.
9. **Dependencies.** Crates from `marigold` are git dependencies on `https://github.com/marigoldcash/marigold` pinned by `rev` (moved to a `tag` whenever a release tag exists at or after the pin). The crate names are still `kaspa-*`. No other git dependency without a note in this file.

## Architecture (fixed; do not redesign in a step)

One binary, `marigold-pool`, one process on pve3 beside `marigoldd`, one SQLite file. The bridge from `marigold` runs **in-process** as a library (`kaspa_stratum_bridge::listen_and_serve_with_shutdown`) and reports accepted shares and found blocks through a `PoolSink` trait added in M1. Rewards are discovered as **coinbase UTXOs arriving at the pool's own address** (not from "block found" events, which are kept for display only): every coinbase output at that address is pool income, allocated once, by outpoint, when mature. Allocation is **PPLNS by DAA-score window**. Payouts are **transparent sends** from the pool wallet to the address each miner logged in with, batched, idempotent. The API is read-only axum with one static dashboard page.

```
ASIC / CPU wallet ──stratum──▶ bridge (in-process, kaspa-stratum-bridge) ──PoolSink──▶ broadcast channel ──▶ accountant ──▶ SQLite
                                   │ gRPC 127.0.0.1:26210                                                        ▲
                                   ▼                                                                             │
                               marigoldd (--utxoindex) ◀── gRPC get_utxos_by_addresses(pool address) ── reward watcher
                                   ▲
                                   └── wRPC borsh 127.0.0.1:27210 ◀── pool wallet (kaspa-wallet-core) ◀── payout engine
API :8788 (axum, read-only, /metrics) ◀── SQLite
```

Crates in the pool workspace: `pool-domain` (types, units, allocation), `pool-db` (sqlx SQLite, migrations, repositories), `pool-accountant` (sink → shares, reward watcher, allocation runner), `pool-payout` (wallet, payout cycle), `pool-api` (axum), `pool-chain` (the `Chain` trait and its backends), `marigold-pool` (binary, config, wiring). **`Chain`** is the one place a chain is named: `ticker()` (`MAGLD`/`KAS`), `unit_name()` (`petal`/`sompi`), `address_prefix(network)`, `default_grpc_port(network)`, `default_wrpc_port(network)`, `coinbase_maturity_daa()`, `validate_address(&str)`, plus the two factories `start_bridge(config, sink, shutdown)` and `open_wallet(data_dir, secret, wrpc_url) -> Box<dyn Payer>` and `node_view(grpc) -> Box<dyn NodeView>`. Two backends behind mutually exclusive cargo features: `chain-marigold` (the default; `kaspa-*` crates from `marigoldcash/marigold`) and `chain-kaspa` (`kaspa-*` crates from a `marigoldcash/rusty-kaspa` branch `pool-sink` that carries only M1's bridge hook cherry-picked onto the upstream release). One binary per chain, both named `marigold-pool`, published side by side; linking both chains into one process is deliberately not done (two nodes and two wallets are needed anyway, and the binary would double). Node access goes through two small traits with in-memory fakes for tests: `NodeView` (virtual DAA score, UTXOs by address, block colour) and `Payer` (send petals to outputs, confirm a transaction).

Fixed numbers (both chains unless noted): 10 blocks per second; coinbase maturity 1,000 DAA (100 seconds × 10 BPS, `COINBASE_MATURITY_SECONDS` in `marigold/consensus/core/src/config/constants.rs`); Marigold testnet address prefix `marigoldtest`, gRPC testnet port 26210, wRPC borsh testnet port 27210; Kaspa prefixes `kaspa`/`kaspatest`, gRPC 16110 mainnet and 16210 testnet-10, wRPC borsh 17110/17210; stratum ports during the soak `:5570` (share difficulty 4) and `:5571` (2048); at cutover the bridge's `:5555`–`:5561` set from `marigold/bridge/config.yaml`.

- [x] **M1 — [marigold] The bridge learns to report to a pool.** Four small additions to `marigold`, each with a test, nothing else. (a) In `bridge/src/share_handler.rs` add `pub struct ShareEvent { address: String, worker: String, difficulty: f64, hash_value: f64, daa_score: u64, blue_score: u64, timestamp_ms: u64 }`, `pub struct BlockEvent { address, worker, hash: String, blue_score, daa_score, nonce: u64, timestamp_ms }` and `pub trait PoolSink: Send + Sync { fn share_accepted(&self, e: ShareEvent); fn block_found(&self, e: BlockEvent); }`. `ShareHandler` gets `with_sink(instance_id, Arc<dyn PoolSink>)`; the default constructor keeps a no-op sink. `share_accepted` is called exactly where `record_share_found` is called today (one place, in `handle_submit`), with the address from `ctx.wallet_addr`, the worker from `ctx.effective_worker_name()`, difficulty and `hash_value` from `state.stratum_diff()`, and `daa_score`/`blue_score` from the header of the `current_job` already in scope. `block_found` is called where `record_block_accepted_by_node` is called (block accepted by the node; the later "confirmed blue" check stays as it is). (b) `GlobalConfig` in `bridge/src/app_config.rs` gets `pool_address: Option<String>`; `ClientHandler::new` takes it; every `get_block_template(` call in `bridge/src/client_handler.rs` passes `pool_address` when set and the client's own address otherwise. The authorized address is still recorded on the context unchanged, so the events carry the miner's identity. (c) `listen_and_serve_with_shutdown` gets a sibling `listen_and_serve_with_sink(config, kaspa_api, concrete, shutdown_rx, sink: Arc<dyn PoolSink>)` that builds the `ShareHandler` with the sink; the existing function calls it with the no-op sink. (d) In `consensus/pow/src/lib.rs` add `State::from_pre_pow(pre_pow_hash: Hash, timestamp: u64, target: Uint256) -> State` (the three fields built exactly as `State::new` builds them from a header), and a `pub fn target_for_stratum_difficulty(diff: f64) -> Uint256` in a new `consensus/pow/src/stratum.rs` that moves `diff_to_target` out of `bridge/src/hasher.rs` (the bridge calls the new function; behaviour identical — the bridge's existing tests on it must still pass). Tests: a bridge test that drives `handle_submit` through the existing test harness in `bridge/src/tests.rs` with a recording sink and asserts one `ShareEvent` with the right fields for an accepted share and none for a low-difficulty one; a test that `pool_address` wins over the client address in the template request (fake `KaspaApiTrait` records the address it was asked for); a pow test that `State::from_pre_pow` of a header's pre-pow hash, timestamp and target gives the same `calculate_pow(nonce)` as `State::new(&header)`. Commit, push to `marigold` `main`, and move the pool's `rev` pin to that commit. ✅ *Verify:* `cargo test -p kaspa-stratum-bridge -p kaspa-pow` green on pve3 in the `marigold` checkout; the pool workspace builds against the new pin with `CHECK=1`.

- [x] **M2 — Domain and database.** `pool-domain`: `Amount(u64)` in the chain's smallest unit with `Display` through the `Chain` ticker (`12.34 MAGLD`; the type is named `Amount`, and the word petal appears only in Marigold's `Chain::unit_name`), `MinerAddress` (validated through `Chain::validate_address`, prefix must match the configured network), `WorkerName`, `ShareWeight(u64)` = `round(difficulty × 1000)`. `pool-db`: `sqlx` SQLite pool in WAL mode, `migrations/0001_init.sql` with tables `miners(address PK, first_seen, last_seen)`, `shares(id PK, address, worker, weight INTEGER, hash_value REAL, daa_score INTEGER, ts_ms INTEGER)` with an index on `daa_score`, `blocks(hash PK, address, worker, blue_score, daa_score, nonce, ts_ms, blue INTEGER NULL)`, `rewards(outpoint PK, amount INTEGER, block_daa_score INTEGER, seen_ts_ms, allocated_ts_ms NULL)`, `balances(address PK, balance INTEGER, total_earned INTEGER, total_paid INTEGER)`, `allocations(reward_outpoint, address, amount INTEGER, PK(reward_outpoint,address))`, `payouts(id PK, idempotency_key UNIQUE, address, amount INTEGER, status TEXT, txid TEXT NULL, created_ts_ms, updated_ts_ms)`, `meta(key PK, value)`. **One database file for the whole pool, never one per miner** (allocation joins every miner's shares on every reward). Locking rule, so `SQLITE_BUSY` never appears: WAL mode, `busy_timeout` 5 s, **one writer connection** (`SqlitePoolOptions::max_connections(1)` for the write pool) that every writing task uses — the share consumer (batched), the reward watcher, the allocation runner, the payout cycle — and a separate read-only pool for the API; SQLite allows any number of readers beside the single writer in WAL mode, and the write load is small (an ASIC on vardiff sends about 30 shares a minute, so a hundred workers is 50 rows a second, batched into a few inserts). Repository functions (runtime `sqlx::query`, no compile-time macros): insert share, shares in a DAA window, prune shares below a DAA score, upsert miner, insert block, record reward if new, list unallocated rewards, apply an allocation atomically (allocations + balances in one transaction, rejected if the reward is already allocated), balances eligible above a threshold, create/update payout. Tests run on `sqlite::memory:` with the migrations applied: every function round-trips; applying the same allocation twice fails the second time and leaves balances unchanged. ✅ *Verify:* `TEST=1 scripts/remote-build.sh` green; `sqlx` migration applies to a fresh file and a second run is a no-op.

- [x] **M3 — Shares flow from the bridge.** `pool-accountant`: `BroadcastSink` implements `PoolSink` by pushing `PoolEvent::{Share, Block}` onto a `tokio::sync::broadcast` channel (capacity 4096; a lagged receiver logs a warning with the count and continues). A consumer task writes shares and blocks to the database in batches (flush every 250 ms or 500 rows), upserts miners, and prunes shares older than `window_daa × 2` below the latest seen DAA score. Tests: feed 10,000 synthetic share events through the sink and consumer and assert the row count, the per-address weight sums and the prune boundary; a block event becomes a `blocks` row. ✅ *Verify:* tests green on pve3.

- [x] **M4 — Rewards are found as coinbase UTXOs.** `NodeView` trait in `pool-accountant` with a gRPC implementation over `kaspa_grpc_client` (`get_virtual_daa_score`-equivalent via `get_block_dag_info`, `get_utxos_by_addresses`, and `get_block` for colour) and an in-memory fake. The reward watcher polls every 10 s: every UTXO at the pool address with `is_coinbase == true` is recorded in `rewards` by outpoint on first sight (immature included, so a later spend cannot lose it); a reward is mature when `virtual_daa_score − block_daa_score ≥ 1000`. The `blocks` table gets its `blue` column filled by asking the colour of each unresolved block hash up to 60 s after it was found (display only). Tests with the fake: a UTXO seen immature then spent is still a reward; a reward is recorded once across restarts; maturity flips at exactly 1,000. ✅ *Verify:* tests green; against the live testnet node on pve3 (`127.0.0.1:26210`) a one-off `marigold-pool rewards --address <founder's testnet mining address>` lists that address's coinbase UTXOs with maturity, read-only, matching `marigold-cli` balance for the same address to within the immature set.

- [ ] **M5 — Allocation (PPLNS by DAA window).** Pure function in `pool-domain::allocation`: `allocate(reward: Petals, fee_bp: u16, shares: &[(MinerAddress, ShareWeight)]) -> Allocation { fee: Petals, per_miner: Vec<(MinerAddress, Petals)> }` where the fee is `reward × fee_bp / 10_000` (integer, floor), the rest is split in proportion to summed weight by the largest-remainder method so that fee + Σ per_miner == reward exactly, with ties broken by address order; an empty share set allocates everything to the fee. The runner in `pool-accountant` takes each mature, unallocated reward, loads shares with `daa_score` in `(block_daa_score − window_daa, block_daa_score]`, calls `allocate`, and applies it atomically through M2's repository (the fee goes to the balance row `pool`). Config: `window_daa` default 36,000 (one hour), `fee_bp` default 100 (1%). Tests: exact-sum property over random inputs (1,000 cases with a seeded RNG), determinism, the empty case, a window-boundary case (a share at exactly `block_daa − window` is excluded, at `block_daa` included), and a runner test with the fake node where two rewards allocate against overlapping windows and balances come out as computed by hand in the test. Read Kat Pool's `accountant/src/allocation.rs` once for comparison; do not copy it. ✅ *Verify:* tests green on pve3.

- [ ] **M6 — The pool wallet and payouts.** `pool-payout` works only through `Payer`; the Marigold `Chain` backend opens the pool's wallet the way the faucet does (`marigold/faucet/src/main.rs`, `connect_wallet` and `cmd_init`): `kaspa_wallet_core::Wallet::try_with_rpc` over wRPC borsh to `127.0.0.1:27210`, local store at the configured data directory, secret from the environment variable `MARIGOLD_POOL_WALLET_SECRET` (never logged, never printed). `marigold-pool init` creates the wallet and prints its receive address — that is the pool address for the config file. `Payer` trait with the wallet implementation (`account.send(PaymentDestination::PaymentOutputs(..), None, Fees::SenderPays(0), None, secret, None, &abortable, None)`, one transaction per batch of at most 50 outputs) and an in-memory fake. Payout cycle, on a schedule (`payout_cron`, default daily at 05:00 host time) and also on `marigold-pool payout --now`: select balances `≥ min_payout` (default 10 MAGLD), and for each batch, in one database transaction, write `payouts` rows with status `pending` and an idempotency key `payout:<address>:<balance_version>` and subtract from balances; then send; on success set `sent` with the txid, on a permanent error set `failed` and restore the balances; a `pending` row found at startup is resolved by looking the key's transaction up before anything else is sent (never double-pay). After the transaction is accepted, mark `confirmed` and add to `total_paid`. Tests with the fake payer: threshold respected; batching at 50; a crash simulated between "pending written" and "sent" neither double-pays nor loses the amount; a failed send restores balances. ✅ *Verify:* tests green; on pve3 `marigold-pool init` on a throwaway data directory prints a `marigoldtest:` address and the wallet file exists; a `payout --now` against an empty database says, in plain words, that nobody is owed anything yet.

- [ ] **M7 — API, dashboard, metrics.** `pool-api` (axum, bind `127.0.0.1:8788` by default): `GET /health` (node reachable, last share age, database ok), `GET /api/pool` (miners online, workers online, pool hashrate from `Σ hash_value` over the last 10 minutes, blocks found in 24 h, last block time, fee, min payout, window), `GET /api/miner/{address}` (balance, total earned, total paid, workers with last-share age and 10-minute hashrate, recent payouts), `GET /api/blocks?limit=` and `GET /api/payouts?limit=`, `GET /metrics` (Prometheus text: shares accepted, blocks found, rewards seen/allocated, payouts sent/failed, balance total owed), and `GET /` serving one static HTML page (inline CSS, no build step) that shows the pool numbers, lets a person paste their address to see their own page, and uses MAGLD with two decimals and plain words throughout; errors are sentences ("That does not look like a Marigold address. It starts with marigoldtest: on the test network."). Tests: axum handlers against an in-memory database seeded by the test; the address error; `/metrics` parses with the `prometheus` text parser. ✅ *Verify:* tests green; `curl 127.0.0.1:8788/api/pool` on pve3 against a seeded test database returns the seeded numbers.

- [ ] **M8 — [marigold] The CPU wallet joins a pool over stratum.** In `marigold`, `cli/src/miner.rs` gains a stratum client mode used by both `mine start --pool <host:port>` (`cli/src/modules/mine.rs`) and `marigold-cli mine-to <address> [<percent>] --pool <host:port>`: open a TCP JSON-RPC line connection, send `mining.subscribe` with user agent `marigold-cli/<version>`, `mining.authorize` with `<address>.<worker>` (worker = hostname), handle `mining.set_extranonce` (the nonce's leading bytes are the extranonce; `bridge/src/share_handler.rs` around the "Add extranonce" comment is the rule to match — read it first, test both a full 16-hex nonce and the short form), `mining.set_difficulty` (target via `kaspa_pow::stratum::target_for_stratum_difficulty`), and `mining.notify` in the bridge's standard format (`bridge/src/client_handler.rs`, `send_immediate_job`: params are the job id as a string, the pre-pow hash as four `u64` numbers, the timestamp as a number); build `kaspa_pow::State::from_pre_pow(hash, timestamp, target)` per job and hand it to the existing hashing threads; on a solution send `mining.submit` `[<address>.<worker>, job_id, nonce_hex]` and count accepted/rejected replies; reconnect with backoff; `mine status` shows the pool, shares accepted per minute and the share difficulty instead of blocks. The own-node refusal in `miner.rs` stays for own-node mode; in pool mode the payout address is the pool's, so the template is the pool's business. Tests in `marigold`: a stratum notify line captured from the bridge parses to the right pre-pow hash and timestamp; nonce formatting with and without extranonce; an in-process test that starts the bridge test harness and a client against it and sees one accepted share at difficulty 1 (reuse `bridge/src/tests.rs` fixtures). Commit, push, and move the pool's pin. ✅ *Verify:* `cargo test -p kaspa-cli -p kaspa-stratum-bridge` green on pve3; from any machine with testnet access, `marigold-cli mine-to <founder's testnet address> 25 --pool 157.90.15.33:5559` logs accepted shares within two minutes against the bridge already running on the big rig (no pool needed for this check).

- [ ] **M9 — One binary, config, deployment, soak.** `marigold-pool` binary: `pool.toml` with `[network] id = "testnet-10"`, `[node] grpc = "127.0.0.1:26210"`, `wrpc = "ws://127.0.0.1:27210"`, `[pool] address`, `fee_bp`, `window_daa`, `min_payout_magld`, `payout_cron`, `data_dir`, `[api] bind`, `[stratum]` instances mirroring the bridge's `InstanceConfig` (port, `min_share_diff`, `prom_port`), vardiff on with `shares_per_min = 30`; validated at boot or the process exits with a sentence saying which key is wrong. Wiring: bridge with `pool_address` and the `BroadcastSink`, consumer, reward watcher, allocation runner, payout scheduler, API; graceful shutdown on SIGTERM drains the share channel before closing the database. `deploy/marigold-pool.service` is exactly the unit below (the faucet unit's pattern: same user, install root `/opt/marigold`, data root `/var/lib/marigold`). `scripts/deploy.sh` copies the binary to `/opt/marigold/bin/marigold-pool`, the unit to `/etc/systemd/system/`, `pool.toml` to `/etc/marigold/pool.toml` if absent, creates `/var/lib/marigold/pool` owned by `marigold`, and generates `/etc/marigold/pool.env` (`MARIGOLD_POOL_WALLET_SECRET=$(openssl rand -base64 24)`, mode 600, root-owned, only if absent — the faucet role does the same), then prints the two commands it deliberately does not run: `systemctl daemon-reload` and `systemctl enable --now marigold-pool`; starting a service on the rig is the founder's hand. Soak: the founder places `/etc/marigold/pool.env` and runs `init`; the pool runs on `:5570`/`:5571` beside the existing bridge; a CPU wallet from M8 on another machine mines to `:5570`; a test ASIC is pointed at `:5571` only when the founder says so. ✅ *Verify:* after 24 hours on testnet: `GET /api/pool` shows the CPU worker online with a hashrate; `shares` grows; at least one `rewards` row appeared from a coinbase UTXO at the pool address and was allocated (`allocations` rows whose amounts sum to that reward); `payout --now` with `min_payout_magld` lowered for the test sends one transaction and the CPU miner's wallet shows the amount; the pool survives one `marigoldd` restart (reconnects, no duplicate rewards); `journalctl -u marigold-pool` has no `ERROR` lines other than the restart.

The unit, verbatim:

```
[Unit]
Description=Marigold mining pool (testnet-10)
After=network-online.target marigoldd.service
Wants=network-online.target
Requires=marigoldd.service

[Service]
Type=simple
User=marigold
Group=marigold
# The marigold system user has no real home; the wallet library resolves its
# storage under $HOME, so point it at the pool's own state directory.
Environment=HOME=/var/lib/marigold/pool
EnvironmentFile=/etc/marigold/pool.env
ExecStart=/opt/marigold/bin/marigold-pool serve --config /etc/marigold/pool.toml
Restart=on-failure
RestartSec=10
# Drain the share channel and close the database cleanly before the kill.
KillSignal=SIGTERM
TimeoutStopSec=30

NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
ReadWritePaths=/var/lib/marigold/pool

[Install]
WantedBy=multi-user.target
```
